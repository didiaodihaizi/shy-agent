# composer-plus-attachments — brainstorm

## 背景

Composer 底部 `+` 目前为 disabled 占位。用户希望：点击后自绘选择框可「添加技能」「添加文件」；输入区顶部以 chip 展示（参考图）；图片 chip hover 用 popover 预览实图。发送时走完整附件流水线（非仅 UI）。

现状：`/` 选技能只往编辑器塞「使用技能 xxx：」；`ChatRequest` 仅文本；已有 `pickFile` / `listSkills` / `readSkill`。

## 决议链

| # | 问题 | 决定 |
|---|---|---|
| Q1 | 发出时附件如何进 Agent | **演进后定为 C→读图预处理**：图片先交多模态读图，结果再给用户所选模型（非直送用户模型 vision） |
| Q2 | 技能/文件数量 | **B** 技能、文件均可多个 |
| Q3 | 非图片文件 | **B** 一律路径+元数据，靠工具读；图片走读图流水线 |
| Q4 | 技能注入 | **C** 先注入摘要/标题，完整 SKILL.md 仍可工具再读 |
| Q5 | 视觉模型从哪来 | **B** 自动用当前 provider 下带 vision 能力的模型；没有则降级提示 |
| Q6 | 实现路径 | **方案 1** Composer 附件层 + 发送前读图预处理 |

用户澄清（相对最初「C 多模态直送」）：图片应交给多模态模型读取，读完后再把数据交给用户所选模型。

## 方案取舍

1. **Composer 附件 + 发送前读图（采纳）** — UI 与 agent 解耦；用户模型可保持纯文本 API；多一步延迟。
2. 运行时工具化 — 与「先读图再交给所选模型」不一致。
3. 真多模态直送用户模型 — 与用户澄清相反。

## 已批准设计摘要

### UI
- `+` 自绘 popover：「添加技能」「添加文件」
- 技能二级可搜索列表；文件系统多选
- Chip 行在输入区顶部；可 ×；发送成功后清空
- 图片 hover popover 预览；`/` 选技能也写成 chip

### 发送
- `ChatRequest` 扩展 `skills[]`、`attachments[]`
- 发送前：校验 → vision 选型 → 读图 → 组装上下文（技能摘要 + 路径元数据 + imageNotes + 用户正文）→ `runAgent`
- 无 vision / 单张失败：该图降级为路径附件，轻提示，不整单阻断

### 不做
- 独立视觉模型设置页、历史富媒体气泡、非图整文件灌上下文、麦克风等

### 验收要点
- `+` / chip / 图 hover / 多技能多文件 / 读图进上下文且用户模型不收原图二进制 / 降级 / `/` 与 `+` 统一为 chip
